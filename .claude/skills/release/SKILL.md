Release `$ARGUMENTS` in two phases and track their steps as a checklist. **Phase 2 changes GitHub and starts only after the user confirms in chat**; a confirmation for one release never covers the next one, and the store publish at the end of phase 2 needs its own confirmation.

## Accounts

- Repository: `borbiuk/band-play` on github.com, personal account `borbiuk`.
- Every `gh` command runs as `GH_TOKEN=$(gh auth token --user borbiuk) gh … -R borbiuk/band-play`. Never run `gh auth switch`: it changes the global state.
- `git push` goes over SSH and needs the personal key; the default key belongs to another account: `git -c core.sshCommand="ssh -i ~/.ssh/id_rsa -o IdentitiesOnly=yes" push …`. The same applies to `git fetch` when it fails with a permission error.

## Versioning

- Semantic versioning: `patch` for fixes only, `minor` for new features that stay compatible (settings and history stored in `chrome.storage.local` keep working), `major` for breaking changes (for example stored settings or shortcuts that older data cannot be read into, or a removed feature).
- No argument: propose the version from the changes since the last tag (`git log <last-tag>..HEAD`; tags are plain `x.y.z`, without a `v`) and ask the user before changing files.
- `public/manifest.json` is the source of truth. [set-version.sh](../../../.husky/set-version.sh) copies the version to `package.json` and `public/manifest.firefox.json`; [tag-releases.sh](../../../scripts/tag-releases.sh) finds the release commit by that version.

## Phase 1: prepare (local only)

1. **State**: on `master`, `git fetch origin` and confirm `master` is not behind `origin/master`. Only changes that belong to the release are in the working tree.
2. **Version**: set `"version"` in `public/manifest.json`, run `./.husky/set-version.sh`, then `npm install --package-lock-only --ignore-scripts` (it asks first). `git diff package-lock.json` must show only the two root `version` fields.
3. **Release notes**: `RELEASE_NOTES.md` gets a `## x.y.z` section at the top (newest first; the tag script reads these headings): a one-line summary, a blank line, then `### Added`, `### Changed` and `### Fixed` lists as needed. The summary line is also the GitHub Release title. User-visible changes are also in `docs/usage.md` and `LISTING.md`. Write in English and add no attribution lines.
4. **Store images**: there is no skill for them. If the popup, the feed player or the branding changed, tell the user that the store images need a manual update.
5. **Checks**: run `/verify`; every step must pass. Then run `npm run test:live` (smoke test against real bandcamp.com; it needs network) and report its result in step 7. A failure there means Bandcamp changed its markup, not that the build is broken: tell the user and let them decide. Also check for an open `markup-drift` issue (`GH_TOKEN=$(gh auth token --user borbiuk) gh issue list -R borbiuk/band-play --label markup-drift`): the daily `markup.yml` opens it when the tests fail on Bandcamp's current markup, and `master` CI stays red until it is fixed, so report it before releasing.
6. **Commit**: one commit `Release x.y.z: <summary>` with a short bullet list of changes, no co-author or "generated by" lines (git asks for confirmation). The Husky pre-commit hook copies the version, formats, runs `git add -u` (every modified tracked file goes into the commit; stage new files on purpose), rebuilds both targets and writes `artifacts/band-play-build-chrome_<dd-mm-yyyy_hh:mm:ss>_x.y.z.zip` and `artifacts/band-play-build-firefox_<dd-mm-yyyy_hh:mm:ss>_x.y.z.zip` (`artifacts/` is gitignored). It needs `jq` and `zip`.
7. **Stop and report**: the commit hash, the two zip paths, what was verified, the `test:live` result and the `markup-drift` state. Ask the user to test the build locally and to confirm the push.

## Phase 2: publish (after the user confirms)

1. **Push**: `git -c core.sshCommand="ssh -i ~/.ssh/id_rsa -o IdentitiesOnly=yes" push origin master` (git asks for confirmation).
2. **CI**: find the run of the release commit (`GH_TOKEN=$(gh auth token --user borbiuk) gh run list -R borbiuk/band-play --commit <sha>`; it can take a few seconds to appear) and wait for it with `GH_TOKEN=$(gh auth token --user borbiuk) gh run watch <id> -R borbiuk/band-play --exit-status`. All jobs of `build.yml` must pass: `build` (Node 24 and 26), `checks` and `e2e`. On failure stop and report the failing job; the `e2e` job uploads the artifact `playwright-report-e2e`.
3. **Tag**: `DRY_RUN=1 ./scripts/tag-releases.sh` must report `Would tag x.y.z at <release commit>` and no other `Would tag` line (the script tags every `RELEASE_NOTES.md` version that has no tag yet). It picks the **oldest** commit on the branch whose `public/manifest.json` has that version, that is the commit that set it. If the version was set in an earlier commit than the one that should be tagged, tag by hand: `git tag -a x.y.z <sha> -m "Release x.y.z"`. Otherwise run `./scripts/tag-releases.sh`. Check with `git cat-file -p x.y.z` (annotated, tagger is the maintainer), then `git -c core.sshCommand="ssh -i ~/.ssh/id_rsa -o IdentitiesOnly=yes" push origin refs/tags/x.y.z`.
4. **Assets**: copy the newest zips of this version from `artifacts/` to a scratch directory as `band-play-chrome-x.y.z.zip` and `band-play-firefox-x.y.z.zip`. Check `"version"` inside each with `unzip -p <zip> manifest.json` and that the files sit at the archive root (`unzip -l <zip>`).
5. **Notes**: the body of the `## x.y.z` section from `RELEASE_NOTES.md` (without the summary line, which is the title), then an `### Install` block (the two zip names; to try a build without a store, unzip it and load it in Chrome via `chrome://extensions` → Developer mode → Load unpacked, or in Firefox via `about:debugging` → This Firefox → Load Temporary Add-on → `manifest.json`), then `**Full Changelog**: https://github.com/borbiuk/band-play/compare/<previous tag>...x.y.z`. Write it to a scratch file, not the repository.
6. **GitHub Release**: `GH_TOKEN=$(gh auth token --user borbiuk) gh release create x.y.z -R borbiuk/band-play --verify-tag --latest --title "<summary line>" --notes-file <notes> <chrome zip> <firefox zip>`.
7. **Verify**: `GH_TOKEN=$(gh auth token --user borbiuk) gh release view x.y.z -R borbiuk/band-play` lists both assets, and `GH_TOKEN=$(gh auth token --user borbiuk) gh api repos/borbiuk/band-play/releases/latest -q .tag_name` returns `x.y.z`.
8. **Report**: commit, CI run URL, tag, release URL.
9. **Offer the store publish**: ask whether to start the store workflows. They are manual (`workflow_dispatch`), run only on `master`, run `npm run lint` and `npm run test:unit` again, build both packages with `zip.sh` from the current `master` (so `master` must still be at the release commit) and upload them: [publish-chrome.yml](../../../.github/workflows/publish-chrome.yml) to the Chrome Web Store, [publish-firefox.yml](../../../.github/workflows/publish-firefox.yml) to Firefox Add-ons (with a source archive for the AMO review; it exits right after the submission, the review comes later). **Only after the user confirms**, start each one the user chose:
    - `GH_TOKEN=$(gh auth token --user borbiuk) gh workflow run publish-chrome.yml -R borbiuk/band-play --ref master`
    - `GH_TOKEN=$(gh auth token --user borbiuk) gh workflow run publish-firefox.yml -R borbiuk/band-play --ref master`

    The Chrome job needs the `CHROME_PUBLISHER_ID` secret (Chrome Web Store API v2) besides the OAuth secrets. Both jobs use the `store` environment, which may have required reviewers: then the run waits until the maintainer approves it on GitHub. Say so, give the run URLs (`GH_TOKEN=$(gh auth token --user borbiuk) gh run list -R borbiuk/band-play --workflow publish-chrome.yml --limit 1`), and watch them with `GH_TOKEN=$(gh auth token --user borbiuk) gh run watch <id> -R borbiuk/band-play --exit-status` when the user wants. Report the result of each run; a store rejection is handled by the maintainer.
